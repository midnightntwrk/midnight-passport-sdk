# E04.11 Passkey on the p256 arm as the first owner key

**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 7  
**Epic issue:** [#47](https://github.com/midnightntwrk/midnight-passport-sdk/issues/47)  
**Packages:** owner, adapter-browser, core, docs/adr/  
**Readiness:** ready · **Sheet title:** Passkey on p256

## Description

The user creates a passkey, and that passkey is the account's first owner key. The private key never leaves the authenticator. The account contract (ACC) verifies the passkey's own WebAuthn signature on the p256 arm, so every owner call is one user prompt and one remote proof: creating the account, and each grant. A dApp's own calls are not owner calls. They are signed by the dApp's grant key, which in the beta is a software JubJub key, so they need no prompt.

Board title: p256 arm: non-PRF passkeys as owner keys. This is now the only device path: it replaces board story E04.08 (passkey PRF to JubJub key), which is dropped.

In scope: An ADR that records the decision: P-256 through WebAuthn for device keys, no PRF, no secret taken out of the authenticator. It links the contract-side PR when it exists. Create: a discoverable ES256 credential; read its public key; no extra "trial" prompt if the profile can be checked another way. Sign: build the WebAuthn challenge with the digest builder from E04.02 (key providers), call get, check the assertion against the profile the circuit accepts. Re-prompt when the browser returns client data outside the profile. Chromium does this on purpose for about 1 assertion in 5. The origin: the SDK refuses to run on an origin whose length differs from the one the pinned contract build was compiled for, with a typed error. A popup or top-level page only. A cross-origin iframe changes the client data and cannot work. Tests with Chromium's virtual authenticator.

Out of scope: the support list for real devices, which is E04.14 (authenticator support matrix). Deploy and activation, which are E04.12 (wave deploy). Passkeys as grant keys: a passkey grant key would mean a prompt per dApp call. Where the account's other secrets come from, which is E04.20 (account secrets without a passkey-derived secret).

## Acceptance criteria

- The ADR is merged.
- Create returns a public key that the contract's pure circuit accepts in an activation check.
- 200 assertions on the virtual authenticator: every one either passes the profile check or is re-prompted, and none reaches the prover with a profile the circuit refuses.
- The number of prompts per flow is counted in a test and documented: create, activation, one owner call.
- Running on an origin of another length fails before any prompt, with the typed error.
- One owner call signed by a virtual-authenticator passkey is accepted on a local node, on an account made with the provider's deploy scripts, with the proof made by E04.03 (remote prover adapter). Activation from the SDK belongs to E04.12 (wave deploy).

## Open questions

- Which origin does the beta use? The contract is compiled for one origin length (21 bytes today; `https://passport.night` is 22). A change after accounts exist means new accounts.
- Re-prompt only, or also a contract change that accepts Chromium's extra field? Re-prompt costs about 1.25 prompts per signature on average (inferred).
- Do Safari and Firefox produce client data in the accepted profile? Never tested.
