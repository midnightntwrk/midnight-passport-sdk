# E07.01 Inbox entries, the coin store, and deposits into an account

**Epic:** E07 · Payments · **Milestone:** 2 Account management and core actions · **Step:** 9  
**Epic issue:** [#50](https://github.com/midnightntwrk/midnight-passport-sdk/issues/50)  
**Packages:** core  
**Readiness:** ready · **Sheet title:** Coins and inbox

## Description

An account's shielded coins are held by the contract, which keeps no public description of them. Whoever deposits a coin describes it in a 192-byte encrypted inbox entry (MIP-0012, section 6.4). The client keeps the opened descriptions, each with its position in the commitment tree, in a coin store. A spend needs exactly that.

This story delivers the receiving side in `core`: the entry codec, the coin store, the builder for a deposit into an account, and the step that turns a newly received entry into a coin the account can spend. The coin store is a local cache only. It is not backed up; it can always be made again from the chain, which is E07.04 (rebuild the coin store).

Board title: Coin store and encrypted inbox. Rewritten. It now covers the whole receiving side: the entry codec, the coin store, the deposit builder, and making a received coin spendable. The full scan of an account is the new story E07.04.

In scope: The inbox entry codec, version 1: seal a coin description to a recipient's encryption public key, and open an entry. Unknown version, unknown suite or wrong length is refused. It is a rewrite for the browser, with `contract/src/wallet/inbox.ts` in the passport repo as reference: that file uses Node's crypto module. Sealing takes the recipient key as an argument. The caller reads it from the chain when it seals and again for each retry (rule 7, the recipient key at the time of the seal). Opening goes through a function the caller passes in. `core` never stores the encryption secret; in the Passport app the kernel of E03.04 (owner kernel) provides the function. The reference store keeps the secret inside private state, and that part is not taken over. The coin store: several coins per color, keyed by coin identity (nonce, color, value), each with its tree position. Operations: add, mark spent, select one for a spend, total per color. It ports from `contract/src/wallet/witnesses.ts` in the passport repo, including the `held_coin` witness, with `contract/MULTI-COIN.md` in the passport repo as reference. The inbox walk: given a ledger state, open every entry that opens with our function, remove duplicates, and return candidates. It ports from `contract/src/wallet/discovery.ts` in the passport repo. Receiving one coin. When the account's state stream shows a new inbox entry, the client opens it, locates the transaction that wrote it and the coin's tree position, checks the coin's commitment against chain data, and only then adds it to the store as held. Until that check the coin is a candidate: an entry is a claim by the depositor. This is the normal path; E07.04 does the same for a whole account at once. The deposit builder: build a call to `deposit_unshielded` (color, amount) or `deposit_shielded` (coin, sealed entry) for any paying wallet. It first checks that the target is an account contract with the deposit circuits on chain, through the read of E04.15 (partial-deploy binding). `connect` cannot import `owner`, so the builder sits in `core`. Every other story and test that makes a deposit uses it. A versioned, serializable store format, saved through the local persistence of E04.05 (platform adapters). The indexer reads this story needs: the account's state stream and contract state, which the seam already lists, and the tree positions of a transaction's outputs. The read belongs to the indexer seam, whose owner is E04.06 (indexer seam); this story names what it needs and does not add a second client. Codec test vectors shared with the reference implementation.

Out of scope: The full scan and rebuild of a store, which is E07.04. Spending, which is E07.03 (send to a wallet address). Paying another Passport, which is E07.02 (pay another Passport, shielded) and E07.06 (pay another Passport, unshielded). Rotating the encryption key, which is E22.01 (viewing-key rotation on revocation). Any backup of the store: there is none, by design.

## Acceptance criteria

- The codec reproduces the reference vectors byte for byte: an entry sealed by the reference implementation opens here, and the reverse. The same tests pass in a browser and in Node.js.
- An entry with a wrong version, suite or length, or sealed to another key, gives "not ours" and does not throw.
- Two coins of one color are both kept and both selectable. A coin marked spent stays spent when the inbox walk offers the same candidate again.
- The serialized store contains no encryption secret (a test scans it), and it round-trips; an unknown format version gives a typed error.
- On a local node, with an account made by E04.12 (wave deploy) and a test token: a wallet deposits a shielded coin through the deposit builder. The owner's client, which starts with an empty store and is only subscribed to the account, ends with that coin held, with its tree position.
- With the pinned artifact from E05.03 (ACC artifact loader), a local run of a shielded withdraw circuit accepts that coin. No owner signature and no node are needed for this check.
- An inbox entry that describes a coin that does not exist stays a candidate and is never counted as held.
- A deposit aimed at an address that is not an account contract, or that lacks the deposit circuits, is refused with a typed error before any transaction.
- A dependency test shows the codec and the deposit builder are reachable from `core` alone.

## Open questions

- Who defines the shape of the open function: this story, or E03.04 (owner kernel)? A dApp with read access needs the same shape through E17.07 (client read surface).
- The store sits in plain local persistence. Coin descriptions show what the account holds. By our reading they do not let anyone spend, because every spend needs an owner or grant signature.
- When a transaction has several outputs, a coin's position is one of several candidates. The reference settles it from contract events when the indexer has them, and by trying each candidate otherwise. Not measured: how often the second case occurs.
- The inbox only grows. Not measured: the time to walk a long inbox in a browser.
- Does the p256 build of the contract keep the same inbox and entry layout as the build the reference code was written for? Not checked.
- A plain NIGHT deposit to an account is refused by the network today (servicedesk#117, midnight-ledger#761). Not measured on the current stack; the tests use a test token.
