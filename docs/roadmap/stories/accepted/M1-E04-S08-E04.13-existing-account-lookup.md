# E04.13 Existing-account lookup

**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 8  
**Epic issue:** [#47](https://github.com/midnightntwrk/midnight-passport-sdk/issues/47)  
**Packages:** owner  
**Readiness:** ready · **Sheet title:** Recognize the account

## Description

When a user comes back, the SDK finds their account instead of deploying a second one. On the same device this is a local record plus a check on chain. On a wiped or new device nothing local exists, and with P-256 device keys the passkey cannot re-derive the address. That second case needs a design decision, so this story is in two parts.

Board title: Existing-account lookup by passkey.

Part 1, same device, is ready to build. A local account record is written before wave 1 is sent: address, binding version, passkey credential id and public key, deploy state. On return the SDK reads the record, confirms the contract on chain through the indexer seam, and confirms the passkey is an owner key. The states are: no account, deploy in progress (hand over to resume), ready. A guard in the deploy refuses to start when a record or an on-chain account already exists for this passkey.

Part 2, a wiped or new device, needs a design first: pick one pointer from the passkey to the account. Four options are known. The account's name in the passkey's user field, then resolve the name: proposed by the contract owner, not decided, and it needs names, which are blocked from outside. largeBlob on the passkey: not supported on every authenticator, and where it is unsupported the write reports "not written" without an error. A registry keyed by the passkey's public key: the public key can be recovered from two signatures, but the registry is not built. WaaS account metadata: only for users with a WaaS key.

Out of scope: restoring private data on a new device, which is E17.05 (WPP restore).

## Acceptance criteria

- A returning user on the same device reaches "ready" with no deploy transaction sent (test counts transactions).
- A local record whose contract is not on chain gives "deploy in progress" or "no account", never "ready".
- With the indexer unreachable the lookup gives a typed error; it does not report "no account".
- Starting a deploy with an existing record fails with a typed error.
- The lookup tries each binding version the SDK supports.
- Part 2: an ADR names the chosen pointer, and a test on a wiped browser profile finds the account with it.
