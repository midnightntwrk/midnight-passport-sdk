# E03.04 Owner kernel: secret boundary and secret hygiene

**Epic:** E03 · Workspace, seams, and guardrails · **Milestone:** 1 Foundation · **Step:** 4  
**Epic issue:** [#46](https://github.com/midnightntwrk/midnight-passport-sdk/issues/46)  
**Packages:** owner. The error base types come from core, in E03.03 (seam interfaces)  
**Readiness:** ready · **Sheet title:** Kernel boundary

## Description

One small module in `owner`, the kernel, is the only code that holds an account secret in plaintext. The rest of the SDK gets signatures, public keys or ciphertext. Secrets never reach a log or an error.

The list of secrets changed when PRF was dropped. Device keys are now P-256 passkeys, which sign inside the authenticator, so the kernel holds no device key and no passkey-derived secret. It holds what is left.

Board title: Owner kernel secret boundary. This story now also covers board story E03.09 (secret redaction and zeroization), merged here.

In scope: The kernel module and its public API. The secrets it may hold: the encryption (viewing) secret key, the recovery secret, later the WPP account key, and the maintenance authority key if the SDK ends up holding it. Accounts are born with one signing arm and gain others later, so that key stays live, and who holds it is open. A boundary check: nothing outside the kernel imports its internals. Hygiene: byte buffers that held a secret are overwritten after use; kernel errors carry no key bytes; a redaction test. A short doc: what enters the kernel, what leaves it.

Out of scope: where each secret comes from and where it is kept between sessions. That is E04.20 (account secrets without a passkey-derived secret). WPP keys arrive with E17 (private data and backup).

## Acceptance criteria

- An import of a kernel-internal file from another module fails lint or a test.
- The kernel's public API returns no secret type: only public keys, signatures, ciphertext and opaque handles.
- Each kernel function that takes a secret buffer calls `fill(0)` on it before returning; a test checks the buffer after the call.
- A test serializes every kernel error (`String`, `JSON.stringify`, `util.inspect`) with known secret bytes loaded and finds none of them.
- The doc lists each secret, who may ask for an operation with it, and how long it lives in memory.
