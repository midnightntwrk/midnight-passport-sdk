# E06.01 Onboarding flow: passkey creation

**Epic:** E06 · Passport app: onboarding · **Milestone:** 1 Foundation · **Step:** 9  
**Epic issue:** [#49](https://github.com/midnightntwrk/midnight-passport-sdk/issues/49)  
**Packages:** The Passport app. From the SDK: owner, adapter-browser  
**Readiness:** ready · **Sheet title:** Passkey onboarding

## Description

The sign-up screens: a new user creates their account with face or fingerprint. No seed phrase is shown, ever.

The board says "the user sees one passkey prompt". That does not hold with P-256 device keys: the passkey signs every owner call, so creating it is one prompt and activating the account is another. The criterion below is a stated prompt count instead.

Cannot start yet. It needs the component library from E02.01 (app design) and a repository for the Passport app. Neither exists. The SDK side can be tried earlier through E04.21 (example page).

In scope: Screens: welcome, what the passkey does, the prover disclosure with accept and decline, create passkey, hand over to deploy progress. Before any prompt: a device check, and a clear message when the device is not supported. Error states: the user cancels the prompt, the browser asks again (some responses must be re-prompted), the device is unsupported. Copy that says what each prompt is for.

Out of scope: deploy progress, which is E06.02 (deploy progress and balance UI). Returning users, which is E06.03 (returning-user resume). Name claim, which is merged into E08.01 (name claim screen).

## Acceptance criteria

- A new user reaches the deploy step with at most 2 passkey prompts on a supported device, not counting re-prompts; the UI test counts them.
- Each prompt is preceded by a screen that says what it approves.
- No screen shows a seed phrase, a key or a contract address.
- Declining the disclosure ends the flow with no passkey created and nothing sent.
- An unsupported device sees the message before any prompt.
- A cancelled prompt returns to the previous screen and can be retried.
- The screens use only E02.01 (app design) parts, and the flow has an automated UI test with a virtual authenticator.
