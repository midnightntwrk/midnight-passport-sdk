# E03.05 — Wire and binding version axes (spec)

> **Status:** approved · 2026/11/17 · decisions confirmed by the user; ready for
> `spec-driver` to plan it
> **Issue:** [midnightntwrk/midnight-passport-sdk#79](https://github.com/midnightntwrk/midnight-passport-sdk/issues/79)
> (epic E03, [#46](https://github.com/midnightntwrk/midnight-passport-sdk/issues/46); milestone 1 Foundation)
> **Deliverables:** D4, protocol v2 (wire axis); D1, contract binding (binding axis)
> (`docs/proposals/2026-09-25-sdk-deliverables.md`)

## Objective

Give the SDK its two version axes as types and constants, and start the
compatibility matrix. Rule 5 states that the SDK tracks two versions that never
share a number: the **wire** version of the messages in `protocol`, and the
**binding** version of `contract` against a deployed account contract (ACC)
(`sdk-requirements.md`, rule 5; `architecture.md`, Example 7).

This story defines the first parts: the constant, the type, and the
accept-or-refuse helper for the wire axis; the binding type and one named ACC
build. It does not build the full wire version rule (E09.04) or the registry
that maps a deployed ACC to its binding (E05.04).

## Scope

**In** (issue #79):

- `PROTOCOL_VERSION` in `protocol`, exported there and nowhere else, and frozen
  at run time.
- A helper in `protocol` that accepts or refuses a peer's wire version, with a
  typed outcome.
- A `BindingVersion` type in `contract`. It names one ACC build: the compiler
  version, the hash of the artifact manifest, and the WebAuthn origin length the
  build was compiled for.
- `docs/compatibility.md`: one row in the wire matrix, one row in the binding
  matrix (a marked placeholder until the first ACC build is pinned).
- A type test that `BindingVersion` and the wire version type cannot be assigned
  to or from each other.
- A test that `PROTOCOL_VERSION` is exported from `protocol` only.
- The C1 doc-sync (below), if it fits the tranche budget.

**Out:**

- The table that maps a deployed ACC to its binding. That is E05.04 (binding
  version registry, issue #95).
- The full wire version rule for a higher minor and a lower major, and the
  cross-version message tests. That is E09.04 (PROTOCOL_VERSION handling).
- The wire messages themselves (`GrantRequest`, the possession proof, the
  sign-in message). Those are E09 (scoped grants foundation).
- The artifact manifest format and the first ACC build. Those are E05.01
  (issue #75) and E05.03. This story consumes a manifest hash; it does not
  define the manifest.
- The pin table and the toolchain pins in `docs/compatibility.md`. Those belong
  to E03.01 (issue #72).
- The C5 and C6 doc edits. They are recorded as doc-sync candidates and left for
  a later PR.

## Decisions

These follow from the issue, the source docs, and the user's confirmations of
2026/11/17.

| # | Decision | Rationale | Source |
|---|---|---|---|
| D1 | The wire version is a structured `{ major, minor }` value, not a bare number. | The accept-or-refuse helper must tell a major apart from a minor; the comparison reads the two parts directly. | Issue #79 acceptance; user confirmation C1. Refines `architecture.md` Example 7 (see the C1 doc-sync). |
| D2 | The wire version type and `BindingVersion` share no field, so each is already non-assignable to the other in both directions. No runtime brand is added. | Rule 5: the two axes never share a number. Disjoint required fields make the type test pass without a brand that carries bytes on the wire. | `sdk-requirements.md`, rule 5. |
| D3 | `checkProtocolVersion` refuses only a higher major for now; it accepts equal, lower minor, higher minor, and lower major. | Issue #79 names three cases (equal and lower minor accepted; higher major refused). This is the smallest surface; E09.04 adds the full rule and more refusal reasons. | Issue #79 acceptance; user confirmation C2 (option A). |
| D4 | The helper in `protocol` returns a typed outcome value; it does not throw, and it imports nothing. | A pure function keeps `protocol` a leaf package. It cannot use the SDK error base, which lives in `core` with Effect 4; `protocol` must not import `core`. | `architecture.md`, "Dependency rules"; issue #83 (error base in `core`). |
| D5 | A refusal is a value in a discriminated union (`{ ok: false; reason }`), not an `Error`. | The caller (E09.04) maps the reason to an SDK error with a stable `_tag` and `code` at the call site, in `core`. | Issue #83 acceptance. |
| D6 | `PROTOCOL_VERSION` is frozen at run time with `Object.freeze`. | A shared constant must not be mutated by a caller. The `readonly` fields guard the type; `Object.freeze` guards the value. | User review note, 2026/11/17. |
| D7 | `BindingVersion` names one ACC build by its compiler version, its manifest hash, and its WebAuthn origin length. | The contract has no version field. The manifest hash commits to the per-file artifact hashes, including the verifier keys. A build for another origin length has other verifier keys and other addresses. | Issue #79 open questions; user confirmations C3 and C4; ADR 0004; `sdk-requirements.md`, "One p256 profile". |
| D8 | The binding matrix gets a marked placeholder row, not a real build. | No ACC build is pinned yet; E05.01 (issue #75) is unmerged. No compiler version is copied from an unpinned source. | Issue #79 acceptance; `architecture.md`, "contract"; E05.01. |
| D9 | `PROTOCOL_VERSION` and its type live in their own module in `protocol`; `BindingVersion` lives in its own file in `contract`. Each index re-exports it. | E03.08 (issue #82) adds tag constants to `protocol` without editing the version module, and a later story can edit a package index without a clash. | Workspace practice; issue #82 shares `protocol`. |

## Surface and interfaces

Indicative types, to be finalized in the tranche. American English, no outside
dependency.

**Wire axis — `packages/protocol/src/version.ts`, re-exported from `index.ts`:**

```ts
export interface ProtocolVersion {
  readonly major: number;
  readonly minor: number;
}

export const PROTOCOL_VERSION: ProtocolVersion = Object.freeze({ major: 2, minor: 0 });

export type ProtocolVersionCheck =
  | { readonly ok: true }
  | { readonly ok: false; readonly reason: 'higher-major' };

/** Refuses only a higher major. */
export function checkProtocolVersion(
  peer: ProtocolVersion,
  ours: ProtocolVersion = PROTOCOL_VERSION,
): ProtocolVersionCheck;
```

**Binding axis — `packages/contract/src/binding-version.ts`, re-exported from `index.ts`:**

```ts
/** One deployed ACC build. */
export interface BindingVersion {
  /** The Compact compiler version. */
  readonly compiler: string;
  readonly manifestHash: string;
  /** The WebAuthn origin length in bytes. */
  readonly originLength: number;
}
```

`ProtocolVersion` has `major` and `minor`; `BindingVersion` has `compiler`,
`manifestHash`, and `originLength`. The two share no required field, so neither
assigns to the other in either direction. The type test asserts both directions
fail. A bare number or string cannot stand in for either, because each needs its
own required fields. (A runtime brand that would also block a future shape change
is deferred; it needs a parser for peer values, which E09 owns — Q2.)

## Flow

The wire check is the only behavior this story adds.

1. A peer sends its `ProtocolVersion` on a message (E09 defines the message).
2. `checkProtocolVersion(peer)` compares it with `PROTOCOL_VERSION`.
3. A higher major returns `{ ok: false, reason: 'higher-major' }`. Every other
   case (equal, lower minor, higher minor, lower major) returns `{ ok: true }`
   (D3).
4. E09.04 sets the final rule for every case and the caller's next action.

No provider or proving-and-settlement-service step is involved.

## Acceptance criteria

From issue #79, made observable:

1. `PROTOCOL_VERSION` is exported from `protocol` and from no other package. The
   source-scan test loads every built package entry (`packages/*/dist/index.js`)
   and checks that `PROTOCOL_VERSION` is a key of `protocol`'s entry only. This
   catches a re-export, including `export *`.
2. `PROTOCOL_VERSION` is frozen: a write to one of its fields throws at run time
   (a test proves it).
3. `BindingVersion` is exported from `contract`. It cannot be assigned to or
   from the wire version type (the type test proves both directions).
4. `checkProtocolVersion` refuses a higher major with a typed outcome. A unit
   test covers equal, lower minor, and higher major.
5. `docs/compatibility.md` has a wire matrix row and a binding matrix row. The
   binding row is a marked placeholder until the first ACC build is pinned.
6. The two axes cannot be compared or converted in TypeScript: each is
   non-assignable to the other (acceptance 3). This is a compile-time guarantee
   from the disjoint shapes, not a runtime scan.

### The `docs/compatibility.md` change

- **Wire matrix:** set the `PROTOCOL_VERSION` cell of the one row to `2.0`, and

  full rule in E09.04.
- **Binding matrix:** add a `Manifest hash` column and an `Origin length` column

  E05.01)"). The existing "Toolchain pins" section is not touched.

## Open questions

- **Q1 — the full wire rule.** Resolved for this story by D3; the complete rule
  for every case is E09.04.
- **Q2 — a runtime brand.** A runtime brand would keep the two axes
  non-assignable even if their fields ever align, but it needs a parser that
  validates a peer value and stamps the brand. That parser is an E09 concern
  (it reads untrusted wire input). Deferred.
- **Q3 — the network id on the wire.** Whether a wire message carries the
  network id is an E09 message-format question; this story does not decide it.
