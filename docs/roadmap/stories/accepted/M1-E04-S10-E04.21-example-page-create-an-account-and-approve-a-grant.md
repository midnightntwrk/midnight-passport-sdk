# E04.21 Example page: create an account and approve a grant

**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 10  
**Epic issue:** [#47](https://github.com/midnightntwrk/midnight-passport-sdk/issues/47)  
**Packages:** examples/passport-page (not published), CI  
**Readiness:** ready · **Sheet title:** none (new story)

## Description

A bare page in the SDK repo, using only the public API of `owner`, where a person creates an account on Preview with a passkey and later approves a dApp's grant request. It is the end-to-end test of this epic, and it is what beta users open, because the Passport app does not exist yet: its screens (E06 (Passport app: onboarding) and E12.01 (authorizer screens)) wait on the brand work and on an app repo.

The board has the grant approval logic in E10.02 (authorizer page, in `owner`) and its screens in E12.01. Neither is a page a user can open without the app. This story is that page.

Proposed by the provider. This story is not on the board.

Slice 1, the account, lands with the account milestone. It is one page under `examples/passport-page`, with no design system, built with Vite. Its steps are: prover disclosure, create passkey, deploy with progress, activate, one owner call, and "come back" (reload and find the account). It has an automated run in headless Chromium with a virtual authenticator against a local node, in CI, and a manual mode against Preview with the hosted sponsor and prover. It also has a wipe button, a count of passkey prompts, and a timing line per step.

Slice 2, grant approval (complete when E04.22 (add circuits to a live account) lands). The page receives a grant request by redirect, shows who asks, the scope in plain words and the expiry, and takes approve or decline. On approve there is one passkey prompt, the grant is issued, and the user is sent back to the dApp. A new user who arrives with a request creates the account first, then sees the request. The CI run gains a stub dApp on a second origin that requests a grant and gets its answer.

Out of scope: brand, copy and layout. Name claim. Listing and revoking grants. Agents.

## Acceptance criteria

- Slice 1: the CI run creates, activates and reuses an account on a local node with no manual step.
- Slice 1: on Preview, a person with a laptop passkey gets from the first click to an activated account, and the wallet behind the page holds no funds.
- Slice 1: reload on the same browser profile lands on the same account without a deploy.
- Slice 2: in CI, the stub dApp's request is approved on the page and the grant is on chain; a declined request issues nothing.
- Slice 2: the page shows the scope text that `owner` produces and adds none of its own.
- Slice 2: a request from an origin other than the one named in it is refused before any prompt.
- The page imports only published entry points; a lint fails on a deep import.
- The run prints prompts and seconds per step, and the README states the numbers from the last Preview run.
