# E03.05 Wire and binding version axes

**Epic:** E03 · Workspace, seams, and guardrails · **Milestone:** 1 Foundation · **Step:** 4  
**Epic issue:** [#46](https://github.com/midnightntwrk/midnight-passport-sdk/issues/46)  
**Packages:** protocol, contract, docs/compatibility.md  
**Readiness:** ready · **Sheet title:** Version axes

## Description

The SDK tracks two versions that never share a number (rule 5, the version axes): the wire version of the messages in `protocol`, and the binding version of the `contract` package against a deployed account contract (ACC). This story adds both as types and constants and starts the compatibility matrix.

In scope: `PROTOCOL_VERSION` in `protocol`, with a helper that accepts or refuses a peer's version. A `BindingVersion` type in `contract`. It names one ACC build: compiler version, the hash of the artifact manifest, and the WebAuthn origin length the build was compiled for. `docs/compatibility.md`: one matrix for the wire axis, one for the binding axis. A test or lint that no code compares or converts one axis to the other.

Out of scope: the table that maps a deployed ACC to its binding. That is E05.04 (binding version registry). Wire messages themselves, which are E09 (scoped grants foundation).

## Acceptance criteria

- `PROTOCOL_VERSION` is exported from `protocol` and nowhere else.
- `BindingVersion` is exported from `contract` and cannot be assigned to or from the wire version type (a type test proves it).
- A peer with a higher major wire version gets a typed refusal; a test covers equal, lower minor and higher major.
- `docs/compatibility.md` has both matrices, and the binding matrix has a row for the first pinned ACC build or a marked placeholder.

## Open questions

- What identifies an ACC build on chain? Proposed: the hashes of its verifier keys, checked against the manifest. The contract has no version field we know of.
- Does the origin length belong in the binding version? Proposed: yes. A build for another origin length has other verifier keys and other addresses.
