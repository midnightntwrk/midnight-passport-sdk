# E04.20 Account secrets and deploy inputs without a passkey-derived secret (spec and ADR)

**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 1  
**Epic issue:** [#47](https://github.com/midnightntwrk/midnight-passport-sdk/issues/47)  
**Packages:** docs/adr/, docs/. The spike lives outside the packages  
**Readiness:** ready · **Sheet title:** none (new story)

## Description

Decide where each non-passkey input of an account comes from, who holds it, and how a second session gets it back. Under the PRF design one passkey secret derived all of them. With P-256 device keys the passkey only signs, so each input needs a source. The deploy cannot be written until this is settled, because these inputs fix the account address.

Proposed by the provider. This story is not on the board. It covers what board story E04.08 (passkey PRF to JubJub key) gave for free and nothing gives now.

In scope: a spec and an ADR, agreed with the contract owner, that give a source for each of five inputs. The maintenance authority key: accounts are born with the p256 arm only and other arms are added later by maintenance updates, and until it is retired this key can replace any verifier key, which is full control of the account. Open: who holds it, and where. The deploy nonce, which is part of the address. Open: random and stored, or derived from something public. The encryption (viewing) key, which reads the account's private data. Open: its source, its storage, and how a second device gets it. The birth recovery key and wrap, which are constructor inputs and so part of the address. They must be reproducible or stored. The private-state encryption key, which protects local state. Without a secret source it protects nothing. Also in scope: one spike on a local node for the chosen authority-key design.

Three options for the authority key (the provider's judgement, none tested for this use). One: the kernel keeps the key on the device. It is lost with the device, so no arm can be added after that. Two: sign the "add k256 arm", "add JubJub arm" and "retire" updates at birth, keep only the signatures, and delete the key. Signatures are not secret. The limits are that the updates apply in a fixed order, and only for the contract build they were signed for. Three: an operator holds the key. Simple, and a custody risk.

This story is on the path to the beta. The first deploy is strictly p256-only, and the JubJub grant-spend circuits a dApp needs are installed afterwards by a maintenance update, in E04.22 (add circuits to a live account). So every beta account uses the authority after birth. Option two fits that case: sign the grant-spend update at birth and keep only the signature. A fallback for the beta (judgement, not agreed): with no answer before the deploy story starts, beta accounts keep the authority key in browser storage and are throwaway test accounts.

Out of scope: the code, which lands in E04.12 (wave deploy) and E03.04 (owner kernel). Backup of private data, which is E17 (private data and backup).

## Acceptance criteria

- The ADR is merged with one chosen source per row of the table, signed off by the contract owner.
- The spec states exactly which bytes go into the address, so two implementations compute the same one.
- The spike shows the chosen authority-key design adding the JubJub grant-spend circuits to a p256-only account on a local node, or shows why it cannot.
- The ADR states what a user loses when the device is wiped, in one paragraph a product owner can read.
- `docs/sdk-requirements.md` and `docs/architecture.md` no longer describe a passkey-derived secret.

## Open questions

- Is a beta without private data acceptable? Then the encryption key can be random and local for now.
- Deriving any secret from the passkey's user handle is ruled out: any page on the same origin can read the handle.
- Does option 2 survive a contract upgrade? No: new builds have new verifier keys.
