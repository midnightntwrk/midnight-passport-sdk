# E08.01 Name claim screen

**Epic:** E08 · Passport app: the account · **Milestone:** 2 Account management and core actions · **Step:** 11  
**Epic issue:** [#51](https://github.com/midnightntwrk/midnight-passport-sdk/issues/51)  
**Packages:** The Passport app. From the SDK: owner, core  
**Readiness:** ready · **Sheet title:** Claim a name

## Description

One screen where the user picks a free name and registers it. It is reached two ways: as the last, skippable step of onboarding, right after the "account ready" screen of E06.02 (deploy progress UI), and later from E08.04 (account home). The board had two stories for this, one in each app epic. They are one screen.

Board title: Name claim screen. Rewritten. It absorbs board story E06.04 (name claim step after deploy): one screen, reached from onboarding or from the account.

Cannot start yet. It needs the component library from E02.02 (UI components) and a repository for the Passport app. Neither exists.

Blocked from outside. The SDK call it drives, E04.16 (name registration), waits on the name service's move to the current ledger (compact#875).

In scope: Availability while the user types, through the availability check of E04.18 (name resolution), with a short delay between keystrokes and requests. The name rules, read from the shared constants of E04.16 and shown as inline messages. The claim: a line that says what the passkey prompt approves, one prompt, progress, and the result with the fee shown as covered. States: the name was taken in the meantime, the sponsor refuses, the prover is busy. Skip in onboarding and claim later. Copy that says a name is public. Two behaviours wait on changes upstream and are not built until then. Continuing a claim after the tab was closed needs a resume in E04.16, which has none. Hiding the claim once the account has a name needs a lookup from account to name, which E04.18 has only if the name service supports it.

Out of scope: The SDK calls, which are E04.16 and E04.18. Changing or giving up a name, which no name story covers. Subdomains, which are E10.08 (child Passport subdomain).

## Dependencies

**Blocked by:** E04.16 Name registration call; E04.18 Name-to-ACC resolution; E06.02 Deploy progress and balance UI; E02.02 UI component library and interaction patterns. External: a repository for the Passport app. Soft: E08.04 (account home) holds the second entry point.  
**Unlocks:** nothing on the board.

## Acceptance criteria

- UI tests against a stub of the claim call cover every state above. They run before E04.16 (name registration) exists.
- Once E04.16 exists: on a local node, a user skips the name in onboarding, opens the name screen later by its route and claims a name, and the screen shows the result.
- The claim asks for one passkey prompt when no re-prompt occurs, and the screen says what it approves.
- Waiting on an upstream change, not part of done until it exists: a claim interrupted by closing the tab continues on return; an account that has a name is not offered a second claim.

## Open questions

- Does E04.16 (name registration) get a resume for an interrupted claim, and does E04.18 (name resolution) get a lookup from account to name that does not depend on the name service? Until then the app can only remember the name locally, on the device that claimed it.
- If names become the way to locate an account on a wiped device (an option in E04.13 (existing-account lookup)), the name has to be chosen before the passkey is created. Then this screen moves to the front of onboarding.
- Can a name be changed or released, and can an account have more than one? The epic text says the screen may become "Change or add a name".
- Not measured: the time of a name claim with a passkey. No name call has run in tests on the current stack.
