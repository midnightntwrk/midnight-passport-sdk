**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 6

**Readiness:** ready · **Sheet title:** Remote prover

## Description

The SDK sends an unproven transaction to a proving service and gets it back proven. The client never downloads or uploads a proving key.

With P-256 device keys this adapter is on the path of every owner call. The passkey circuits are the largest in the account contract: a proving key of about 470 MB each, which a browser tab cannot prove. And the stock midnight-js client sends the key with every proof request, so the adapter has to do it differently.

In scope: The prover seam implemented over HTTP: send the proof preimage and the circuit id; the service finds the key by itself. A per-user or per-origin credential on each request. No shared secret in page code. Typed errors: queue full (with a retry-after), timeout, rejected input, service down. Only "rejected input" is final. `/check` before `/prove`, so a bad input fails in under a second. Bounded waits and cancel. A contract test against a local proof server, using the smallest account circuit.

Out of scope: the proving service itself (it holds the keys, needs CORS and a memory cap; the provider runs one). In-browser proving, which is E15.02 (WASM prover, after V1). The disclosure text, which is E04.10 (prover disclosure).

## Acceptance criteria

- A proof request for a p256 owner call is under 10 KB on the wire (test measures the body).
- No code path fetches a proving key into the client (test with a network recorder).
- A full queue gives the typed "busy" error with a retry time, and the adapter retries within its bound.
- A request past its deadline is cancelled and gives the typed timeout error.
- The seam's contract test from E03.03 (seam interfaces) passes against a local proof server.
- One p256 activation and one p256 owner call prove through the adapter against the hosted prover on Preview.
