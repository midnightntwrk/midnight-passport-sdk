# E04.12 Account deploy in waves: plan, send, resume, activate

**Epic:** E04 · Account deployment · **Milestone:** 1 Foundation · **Step:** 8  
**Epic issue:** [#47](https://github.com/midnightntwrk/midnight-passport-sdk/issues/47)  
**Packages:** owner, contract  
**Readiness:** ready · **Sheet title:** Deploy in waves

## Description

Deploy a user's account contract (ACC) and activate it with the passkey, with the sponsor paying. The contract's verifier keys do not fit in one transaction, so the deploy goes out in waves: one deploy transaction, then maintenance updates.

As agreed, an account is born with the p256 arm only: 20 of the 52 circuits. In tests, a one-arm account took 2 transactions on another arm; p256 is not tested yet. The first deploy is strictly p256-only. The grant-spend circuits for a dApp's JubJub grant key arrive afterwards by maintenance update, in E04.22 (add circuits to a live account). So this deploy does not retire the maintenance authority. The planner handles any number of waves, because later additions and other builds use it too.

Board title: Multi-wave ACC deploy planner. This story now also holds the deploy half of board story E04.09 (sponsored deploy and starting balance).

In scope: A pure planner: packs verifier keys into waves by pricing each wave against the chain's live block limits, with headroom. No fixed byte budget. The circuit set of the first deploy is read from the manifest, not hard-coded: the p256 arm and the shared circuits, nothing else. The maintenance authority is left live at the end of the deploy, in the form E04.20 (account secrets spec) specifies. Wave 1 is a fixed circuit list per binding version, taken from the manifest. It fixes the address, so the planner never repacks it. The address is computed before anything is sent, from the inputs that E04.20 (account secrets without a passkey-derived secret) specifies. This includes setting the deploy nonce. Send: each wave is paid just before it is sent and the next goes out when the previous is in a block. Any result other than "applied" stops the sequence. Resume: read the contract's state from the chain, work out the next wave, continue. The resume state holds no secret. Activation with the passkey (one prompt, one proof), then a first owner call in the integration test. Progress events for a UI: planned, wave n of m in a block, activated.

Out of scope: adding circuits after birth, which is E04.22 (add circuits to a live account). The starting balance, which is E04.09 (starting balance). Using the account while waves are pending, which is E04.15 (partial-deploy binding).

## Acceptance criteria

- For the pinned artifact the planner gives the same plan on every run, and no wave is above the headroom limit at live parameters.
- On Preview, a client with no funds deploys a p256-arm account at the address computed beforehand, activates it with a virtual-authenticator passkey, and makes one owner call.
- A deploy killed after wave 1 is in a block resumes and finishes without sending wave 1 again and without paying any wave twice.
- A wave that the node refuses is rebuilt and paid again; the old bytes are not resent (test).
- The resume state contains no key (test scans it).
- Two deploys at once through the sponsor both finish.
- On that account, exactly the circuits the manifest lists for birth are on chain, and the authority is still live (checked through the read of E04.15 (partial-deploy binding)).
- The integration test records time and DUST per wave.

## Open questions

- The exact circuit list of the first deploy and of its wave 1. Needed from the contract owner before this story starts, or it slips. Changing it later changes every address.
- Does a p256-only birth need all 20 circuits? The p256 grant-spend circuits are unused if grant keys are JubJub.
- The deploy nonce cannot be set through the midnight-js API. Keep a patch of the serialized intent, or wait for an upstream option?
- Is "in a block" safe enough between waves, or do we wait for finality? Finality costs about 15 s per wave.
