# E08.05 Receive screen and deposit page

**Epic:** E08 · Passport app: the account · **Milestone:** 2 Account management and core actions · **Step:** 11  
**Epic issue:** [#51](https://github.com/midnightntwrk/midnight-passport-sdk/issues/51)  
**Packages:** The Passport app. From the SDK: core  
**Readiness:** to discuss implementation · **Sheet title:** none (new story)

## Description

Receiving. The user shows something a payer can act on, and it is never the account's contract address (rule 3, deposit, not address). Another Passport pays from its own send screens. A wallet that only does address-to-address transfers cannot pay a Passport: someone has to build the deposit call for it. So this story has a receive screen and a public deposit page that an outside wallet opens from a link.

Proposed by the provider. This story is not on the board. It is the receiving half of board story "Transfer and deposit screens".

Cannot start yet. It needs the component library from E02.01 (app design) and a repository for the Passport app. Neither exists.

Partly blocked from outside. A link by name waits on E04.18 (name resolution). A plain NIGHT deposit is refused by the network today (servicedesk#117, midnight-ledger#761).

In scope: The receive screen: the account's name, a link and a QR code that open the deposit page, and incoming payments appearing as they land (from E07.05 (holdings and activity reads)). The deposit page: a public route that needs no Passport account and none of the account screens. It shows the payee and takes an asset and an amount. The payer connects a wallet, the page builds the deposit with the builder of E07.01 (inbox, coin store and deposits), and the wallet signs and submits. What is shared with E15.05 (Pay with Passport). The deposit builder is owned by E07.01 and used by both. Connecting a payer's wallet and driving the deposit from a web page is the part the SDK requirements give to `connect` as Pay with Passport. If E15.05 delivers that part, this page uses it and builds only the page around it. See the open questions. States on the deposit page: no wallet present, wrong network, the wallet refuses, the deposit fails, done.

Out of scope: The deposit builder, which is E07.01. Payment requests from a dApp, which are E15.05. Deposits from other chains, which are E25.03 (ETH and BTC deposit flow). The starting balance, which is E04.09 (starting balance).

## Acceptance criteria

- UI tests with a stub wallet and a stub builder cover every state. They run before E07.01 (inbox, coin store and deposits) exists.
- Once E07.01 exists: on a local node, a test wallet driven through the deposit page makes one unshielded and one shielded deposit. The payee's client receives both, checked through the holdings read of E07.05 (holdings and activity reads).
- A test scans the receive screen's text: the contract address is not printed as text to copy.
- The deposit page is tested in a browser profile with no Passport data.

## Open questions

- What is E15.05 (Pay with Passport)? The SDK requirements say `connect` exposes the deposit as Pay with Passport, for wallets that cannot pay a Passport by themselves. The board and the epic text say a dApp asks for a payment that the user approves in the Passport app, as a deposit joined with the dApp's intent. If it is the first, the wallet connection of this page belongs there. If it is the second, it belongs here. Not decided.
- Without names the link has to identify the account some other way. Is a contract address inside a link acceptable under rule 3, as long as no screen offers it as a payment address? The SDK requirements say a wallet gets the account address from the name service.
- Who pays the fee of a deposit made from an outside wallet: that wallet, or the sponsor? If the sponsor, the limit per caller of E04.01 (sponsor policy) has to cover a public page.
- Not measured: a deposit made by a browser wallet through the wallet connector. In tests, deposits came from scripted wallets only.
- Does the deposit page live in the Passport app's origin, or on its own?
