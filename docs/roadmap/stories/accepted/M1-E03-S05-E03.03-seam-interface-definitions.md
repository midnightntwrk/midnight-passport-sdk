# E03.03 Seam interface definitions

**Epic:** E03 · Workspace, seams, and guardrails · **Milestone:** 1 Foundation · **Step:** 5  
**Epic issue:** [#46](https://github.com/midnightntwrk/midnight-passport-sdk/issues/46)  
**Packages:** core, dev, docs/adr/, docs/architecture.md  
**Readiness:** ready · **Sheet title:** Seam interfaces

## Description

Write the typed interfaces (seams) that adapters implement, so the prover, the sponsor, the indexer and the platform can be swapped without touching the libraries. First settle the seam list, because the docs disagree: the architecture lists 12 seams and no indexer, the board story lists 9, and the registry seam sits in `contract` in one and `core` in the other.

In scope: an ADR with the seam list, and `docs/architecture.md` brought in line with it; interfaces and a local stub for the seven seams that E04 (account deployment) needs; the SDK error base types (`_tag`, `code`, no secret fields).

The proposed seam list, pending the ADR. In `core`, written in this story: key provider, prover, broadcast, fees, platform, account metadata, and a new indexer seam for chain reads and transaction status. In `core`, written later: private state and storage with E17.01 (WPP client and storage seam), and multi-chain with E25.01 (multi-chain interface), after V1. In `contract`: the registry seam, written with the dApp artifact loader, which moves to the agents epic. In `owner`: recovery with E21.02 (guardian transport) and DID with E24 (identity).

Out of scope: any adapter implementation. Seams marked for a later story get no code here.

## Acceptance criteria

- The ADR is merged and the seam table in `docs/architecture.md` matches it, with the indexer seam added.
- The seven interfaces compile in `core` and export no Effect, rxjs or midnight-js type (the guard from E03.10 (Effect 4 inside the SDK) passes).
- Reads that change over time use `subscribe(listener) => unsubscribe` with `current()`; writes return Promises.
- Each of the seven seams has an in-memory stub in the `dev` package and a contract test that the stub passes. Adapters reuse that test later.
- The key provider signature is async and allows one user prompt per signature (a passkey signs every call).
- The prover seam takes an unproven transaction and never a proving key.

## Open questions

- Is Fees a seam of its own, or part of Broadcast? In our tests the sponsor pays each transaction just before it is sent, so the two always act together.
- Where does plain local persistence go (the local account record, the deploy resume state)? Proposed: the Platform seam. The Storage seam stays for ciphertext only.
- Does the registry seam stay in `contract`? Proposed: yes, as the architecture has it.
