## Summary

- The kernel in `owner` is the only code that holds an account secret in
  plaintext. Everything else gets a signature, a public key, ciphertext, or an
  opaque handle.
- The kernel is a `Kernel` object, one per account, not a module-global. A
  `dispose` call zeros every secret it still holds.
- The kernel has one public entry. A boundary test rejects any import from
  another module into a kernel-internal file.
- The kernel zeros a secret buffer after use, on return and on a throw.
- A kernel error carries no key bytes. A test proves it.
- A short doc records each secret, who may ask for an operation with it, how
  long it lives in memory, and what enters and leaves the kernel.
- The secret list stays open where the issue keeps it open. E04.20 (#74) decides
  the final list. The issue is the source for this story.

Source of truth: `architecture.md` ("The owner kernel invariant", "What leaves
the kernel", "Dependency rules"), `sdk-requirements.md` (rules 4, 11, and 12),
and the E03 epic ("The owner kernel boundary").

## Decisions

1. **One kernel holds the secrets.** The kernel in `owner` is the only code
   that holds an account secret in plaintext. Everything else gets a signature,
   a public key, ciphertext, or an opaque handle.
   _Source: `architecture.md`, "The owner kernel invariant"; `sdk-requirements.md`,
   rule 4; E03 epic._

2. **One public entry; the rest is internal.** The kernel has one public entry
   file. Every other file under the kernel folder is internal. "Another module"
   means any source file outside the kernel folder. An import from another
   module into an internal file is a boundary violation. The kernel's own unit
   tests are the one exception (Decision 10).
   _Source: acceptance criterion 1; the existing dependency-boundary pattern
   (`tests/dependency-rules.test.mjs`)._

3. **The package does not re-export the kernel.** The public package entry of
   `owner` stays empty for now, and the package adds no `./kernel` subpath to
   its `exports`. The kernel is owner-internal, so the secret-holding surface
   stays out of the published API.
   _Source: `architecture.md`, "The owner kernel invariant"; the package entry's
   current placeholder._

4. **The public API returns no secret.** The public API returns a public key, a
   signature, ciphertext, or an opaque handle. A handle exposes no byte
   accessor. The design has one exception, and it is out of scope here: the
   viewing key leaves the kernel whole to a holder of a read grant, after a
   separate consent. That export belongs to the read-access lifecycle (E17).
   See Open question 4.
   _Source: acceptance criterion 2; `architecture.md`, "What leaves the kernel";
   `sdk-requirements.md`, rule 13._

5. **The helpers stay internal.** `zeroize`, `withSecret`, and `withSecretAsync`
   run plaintext through a caller-supplied function, so they are internal. They
   are not on the public entry. A generic helper on the public entry could
   return secret bytes, which Decisions 1 and 4 forbid. The kernel's own tests
   exercise them (Decision 10).
   _Source: Decisions 1 and 4._

6. **Zero a secret buffer after use.** A kernel function that takes a secret
   buffer calls `fill(0)` on it before it returns. It also zeros the buffer on a
   throw, so an error path leaves no secret behind. The zeroing runs in a
   `finally`.
   _Source: acceptance criterion 3; E03 epic ("buffers are zeroed after use")._

7. **No secret in a log or an error.** A secret never reaches a log or an error.
   A kernel error carries no key bytes.
   _Source: the issue; E03 epic ("Secrets never appear in logs or errors"). The
   docs today state this only for the recovery secret (`sdk-requirements.md`,
   "Recovery"; `architecture.md`, "Recovery", point 3). See Doc conflicts._

8. **The source stays platform-neutral.** `owner` source imports no `node:*`
   module. Zeroing uses `Uint8Array.fill`. The serialization checks
   (`util.inspect`) run in test files only, which build with the Node types.
   _Source: `architecture.md`, Dependency rule 7; the `owner` source build
   (`types: []`)._

9. **A fixed-message built-in error until the base types land.** Until the
   `core` SDK error base types exist (E03.03, #84), the one first-tranche reject
   case throws a built-in `Error` with a fixed message (Decision 11). No message
   interpolates an input or a secret. The error taxonomy and the redaction hooks
   replace this throw in the later tranche.
   _Source: Decision 7; the blocked-by relation to #84._

10. **One test folder may reach internals.** The `owner` package's own test
    folder may import kernel internals, so a unit test can exercise the internal
    helpers (`zeroize`, `withSecret`, `withSecretAsync`). The boundary check
    exempts exactly this path. No other module, and no other package's tests,
    may reach an internal. The retained store is a private field (Decision 13),
    so the tests check the handle lifecycle through behavior; the `zeroize` unit
    test and code review cover the zeroing of the retained copies.
    _Source: acceptance criterion 3; Decisions 2 and 13._

11. **The one reject case in the first tranche.** The first-tranche surface does
    not validate inputs. The one reject case is `releaseSecret` called with a
    handle that the kernel already released or never issued. It throws
    (Decision 9).
    _Source: the first-tranche surface below._

12. **The secret list stays open.** The kernel names the secrets the issue names
    now, and marks the rest open. It does not freeze the list.
    _Source: the issue; E04.20 (#74)._

13. **The kernel is instance-scoped and disposable.** The kernel is a `Kernel`
    object, not a module-global. One is created per account, and one process
    can hold several accounts without their secrets colliding. The retained
    store is a private field. `dispose` zeros every secret the kernel still
    holds, which gives a single teardown point (for example on lock or logout).
    _Source: the code-style rule "no module-global singletons — instance-scoped,
    disposable objects; multi-account must be possible"._

## Surface and interfaces

First-tranche surface. It covers only what the acceptance criteria need. The
per-secret operations wait on #74.

The sole public entry: `packages/owner/src/kernel/index.ts`.

```ts
/** An opaque handle to a secret a kernel holds. It exposes no byte accessor. */
export class SecretHandle {
  // A private field makes the type opaque and nominal. A kernel mints the
  // handle; no caller can read the bytes through it.
  readonly #kernel = true;
}

/**
 * A kernel: the only object that holds an account's secrets in plaintext.
 * Create one per account with `new Kernel()`, and `dispose` it to zero every
 * secret it still holds (Decision 13).
 */
export class Kernel {
  /**
   * Copies `bytes` into this kernel, then zeros the caller's `bytes`. Returns
   * an opaque handle. The copy lives until `releaseSecret` or `dispose`.
   */
  holdSecret(bytes: Uint8Array): SecretHandle;

  /** Zeros the retained copy and invalidates the handle. */
  releaseSecret(handle: SecretHandle): void;

  /** Zeros every secret this kernel still holds, and empties its store. */
  dispose(): void;
}
```

Internal, under the kernel folder, not on the public entry (Decision 5):

```ts
/** Overwrites a secret buffer in place with zero bytes. */
function zeroize(buffer: Uint8Array): void;

/**
 * Runs `use` with the secret, then zeros `secret` in a `finally`. Returns the
 * public result of `use`.
 */
function withSecret<T>(secret: Uint8Array, use: (secret: Uint8Array) => T): T;
function withSecretAsync<T>(
  secret: Uint8Array,
  use: (secret: Uint8Array) => Promise<T>,
): Promise<T>;
```

Notes:

- A secret's lifetime in memory: a `withSecret` buffer lives only for the
  callback; a held secret lives from `holdSecret` to `releaseSecret`, or at most
  to `dispose`. The doc records this generic model, and records the per-secret
  policy from the design (for example, the recovery secret exists only during a
  session or a recovery).
- A kind label for each held secret, and the per-secret lifetime typing, arrive
  with #74, when the secrets are named.
- The kernel keeps the retained copies in a private field on the `Kernel`
  instance, not in a module-global store (Decision 13).
- The `owner` tests reach the kernel through its built output under `dist/` (for
  example `../dist/kernel/index.js`), because the package entry does not
  re-export the kernel. The root `test` script builds before it runs the tests,
  and the test project references the source project, so the declarations exist.

## Flow

No provider and no proving and settlement service are involved. The kernel holds
a secret in memory, derives a public output, and zeros the buffer. There is
nothing to prove or submit, so there is no settle path here.

## Acceptance criteria

1. A source file outside the kernel folder that imports a kernel-internal file
   fails the boundary test. (T1)
2. The kernel's public API returns no secret type: only public keys,
   signatures, ciphertext, and opaque handles. A handle exposes no byte
   accessor. (T1)
3. Each kernel function that takes a secret buffer calls `fill(0)` on it before
   it returns, and on a throw. A test enumerates the functions that take a
   secret buffer and checks each buffer after the call. (T1)
4. Every kernel error, serialized with `String`, `JSON.stringify`, and
   `util.inspect` with known secret bytes loaded, contains none of those bytes.
   (T2, blocked by #84)
5. The doc lists each secret the kernel may hold, who may ask for an operation
   with it, and how long it lives in memory, and it states what enters and
   leaves the kernel. (T1)

## Open questions

1. `architecture.md` and the E03 epic still list the PRF output and the JubJub
   device key as kernel secrets. PRF was dropped. E04.20 owns the sync. See Doc
   conflicts.
2. `architecture.md` lists the guardian secret among the kernel's secrets; the
   issue does not name it. The kernel names it where it holds it, but whether it
   belongs in the frozen secret list waits on E04.20.
3. The issue lists the maintenance authority key as a secret the kernel may
   hold, "if the SDK ends up holding it." The docs are silent on it. Open until
   E04.20.
4. Acceptance criterion 2 says the public API returns no secret type.
   `architecture.md` says the viewing key leaves the kernel whole to a read-grant
   holder, and a WPP package key goes to a dApp at the handoff. Those exits are
   later stories (E17). The invariant here holds for the kernel's foundational
   surface. The one documented exception, the viewing key whole after a separate
   consent, arrives with the read-grant lifecycle. Stated so this spec does not
   contradict the architecture.
5. JavaScript cannot promise that memory is erased: strings and engine copies
   remain. The criteria test what is testable (a zeroed buffer, a redacted
   error). Is that enough for the security review? (from the issue)
6. A non-extractable WebCrypto key could hold some secrets outside page-script
   reach. Worth a spike once E04.20 names the secrets. (from the issue)
